# Lost in the Middle: How Language Models Use Long Contexts

- 一手来源：https://arxiv.org/abs/2307.03172 （PDF 版本为 arXiv:2307.03172v3，2023-11-20；论文致谢注明为 TACL 投稿，action editor 为 Luke Zettlemoyer）
- 作者：Nelson F. Liu、Kevin Lin、John Hewitt、Ashwin Paranjape、Michele Bevilacqua、Fabio Petroni、Percy Liang（Stanford University / UC Berkeley / Samaya AI）
- 代码与评测数据：https://nelsonliu.me/papers/lost-in-the-middle

## 摘要

这篇论文研究一个看似基础却很少被系统回答的问题：语言模型虽然能接收很长的输入上下文，但它们到底能不能用好上下文里的信息？作者设计了两类需要"在输入中定位相关信息"的受控实验——多文档问答（multi-document QA）和合成 key-value 检索——通过分别改变上下文长度和相关信息在上下文中的位置，观察模型性能的变化。核心发现是性能呈 U 型曲线：相关信息出现在开头（primacy bias）或结尾（recency bias）时表现最好，落在中间时显著退化，即便是显式扩长了上下文窗口的模型也不例外。作者进一步从模型架构、query-aware contextualization（把 query 同时放在数据前后）和 instruction fine-tuning 三个角度做了初步归因，并在开放域问答的 retriever-reader 案例中表明：给模型塞更多检索文档的收益远小于预期。论文同时提出了一套评估协议：声称模型能"用好长上下文"，必须证明其性能对相关信息位置不敏感。

## 要点

### 核心发现

- **U 型性能曲线**：在多文档问答中，改变含答案文档的位置会让性能大幅波动——GPT-3.5-Turbo 最多掉 20 个百分点以上；在 20、30 篇文档的设置下，答案放在中间时的表现甚至低于完全不给文档的 closed-book 基线（56.1%）。
- **扩窗不等于会用窗**：当输入同时放得下时，模型与其扩展上下文版本（如 GPT-3.5-Turbo vs. GPT-3.5-Turbo (16K)、Claude-1.3 vs. Claude-1.3 (100K)）的性能曲线几乎重合，说明扩展上下文窗口本身并没有让模型更会利用上下文。
- **合成 key-value 检索同样暴露问题**：这个任务只要求在 JSON 对象里精确匹配 UUID、返回对应 value，刻意剥离了自然语言语义干扰。Claude-1.3 系列在所有长度下接近满分，但 GPT-3.5-Turbo、GPT-3.5-Turbo (16K)、MPT-30B-Instruct 在检索中间位置的 key 时依然出现 U 型退化。

### 实验设置

- **多文档问答**：基于 NaturalQuestions-Open 中 2655 条长答案为段落的查询；每题 1 篇含答案的 Wikipedia 段落 + k−1 篇由 Contriever（MS-MARCO 微调）检索的干扰段落（每段至多 100 token），k 取 10/20/30；指标为 accuracy（预测输出中是否出现标注答案）。closed-book 与 oracle（只给含答案的单篇文档）作为参照，例如 GPT-3.5-Turbo 分别为 56.1% / 88.3%，Claude-1.3 为 48.3% / 76.1%。
- **Key-value 检索**：输入为 k 对随机 UUID 构成的 JSON 对象 + 一个待查 key，k 取 75/140/300（约 4K/8K/16K token），每档 500 个样本。
- **评测模型**：开源侧 MPT-30B-Instruct（8K，ALiBi 位置编码）、LongChat-13B (16K)；闭源侧 GPT-3.5-Turbo(-0613) 及其 16K 版、Claude-1.3 及其 100K 版；另有 GPT-4 (8K) 在 500 例子集上的补充实验（趋势相同、绝对值更高）、encoder-decoder 对照 Flan-T5-XXL / Flan-UL2、MPT-30B base 模型、以及 Llama-2 7B/13B/70B（Appendix D/E）。全部使用 greedy decoding。

### 归因分析（§4）

- **模型架构**：encoder-decoder 模型（Flan-UL2）在训练时序列长度（2048 token）以内对位置变化相当稳健（最好与最差仅差 1.9 个百分点），作者推测双向 encoder 让每篇文档都能在后续文档的语境下被处理；但一旦超出训练长度，同样出现 U 型曲线。
- **Query-aware contextualization**：把 query 同时放在数据之前和之后，让所有模型在 key-value 检索上接近满分（GPT-3.5-Turbo (16K) 在 300 对时从最差 45.6% 升到满分），但对多文档问答的趋势几乎没有改善——只有答案在最开头时略有提升，其他位置反而略降。
- **Instruction fine-tuning**：MPT-30B base 模型同样呈 U 型，说明这一现象不是 instruction tuning 引入的；tuning 只是把最好/最差差距从约 10 个百分点收窄到约 4 个。Appendix E 的 Llama-2 实验显示 U 型曲线只在足够大的模型上出现——7B 只有 recency bias，13B/70B 才是完整的 U 型；作者据此推测早期工作没观察到 primacy bias 是因为模型太小（<1B）。

### 开放域问答案例（§5）

- 在标准 retriever-reader 设置下（Contriever 从 Wikipedia 检索、文档直接塞进 prompt），reader 准确率远早于 retriever recall 饱和：检索 50 篇相比 20 篇只带来约 1.5%（GPT-3.5-Turbo）/约 1%（Claude-1.3）的提升，代价是更长的输入、更高的延迟和成本。
- 作者由此给出的实践建议是 reranking（把相关文档往上下文开头推）和 ranked list truncation（该少检索时就少检索）。
- 论文在 related work 中指出，这个 U 型曲线与心理学中的 serial-position effect（人对列表首尾记忆最好）相似，并认为这在 self-attention 机制上有些意外，因为 attention 在原理上对任意位置的 token 有同等的访问能力。

## 与本库的关系

这篇论文是「Agent Memory / Context」子方向里最常被引用的实证证据之一，对本库多条线索都有直接支撑：

- 对 [[context-manager]]：它给出了 context manager 存在的核心理由——上下文窗口不是"塞进去就能用"的容器，往 prompt 里堆放更多检索结果或历史记录可能适得其反。reranking、truncation、把关键信息放在上下文开头或结尾，正是 context manager 做上下文组装（assembly）时的具体设计依据。
- 对 [[agent-memory]]：agent 的长期记忆最终都要以检索结果的形式回填进上下文，这篇论文说明"检索得到"和"模型用得到"之间有一道鸿沟——记忆的写入、排序和回填位置策略会直接影响下游表现，评测记忆系统时也应检查检索内容被放置的位置。
- 对 [[context-engineering]]：它是 context engineering 作为一门实践的实证起点之一——"更多上下文是 trade-off 而非免费午餐"这一论断，是压缩、筛选、重排等上下文工程手段的前提假设。
- 对 [[agent-harness]]：harness 负责每步为模型组装输入，本文的评估协议（性能应对相关信息位置不敏感、比较 best/worst case 差距）可以直接用来检验一个 harness 的上下文组装策略是否稳健。
- 论文多文档问答的设置模拟的正是 retrieval-augmented generation（RAG）场景，与 [[ai-agent-harness]] 方向页中"上下文来源多样化"的讨论相呼应。

## 可质疑之处

- **时效性**：实验对象是 2023 年中的模型（GPT-3.5-Turbo-0613、Claude-1.3、MPT-30B、LongChat-13B、Llama-2）。此后的模型普遍针对长上下文做了专门训练，U 型曲线在新一代模型上是否仍然成立、程度如何，本文无法回答，引用其结论时应注意这一边界。
- **任务覆盖面窄**：两个任务都是"定位并使用单点信息"，接近 needle-in-a-haystack；需要跨文档聚合、推理的任务上的位置偏置形态可能不同，待验证。
- **归因为初步性质**：作者自己称 §4 是 preliminary investigation。encoder-decoder 更稳健的解释（双向 attention 利于重要性估计）只是 hypothesis；instruction tuning 收窄位置偏置的机制也未被证实。
- **评测协议的成本约束**：GPT-4 只在 500 例子集上做了多文档问答（作者注明全量评测需 6000 美元以上），key-value 检索上没有 GPT-4 数据；闭源模型的结论建立在特定 API 快照上，不可复现性待验证。
- **解码方式单一**：全部实验使用 greedy decoding，采样等其他解码策略对位置偏置的影响留给了 future work。
- **accuracy 指标的粗糙性**：以"标注答案字符串是否出现在输出中"为判定，对答案表述变体、部分正确等情况不敏感；不过作者在 AmbigQA 无歧义子集、随机干扰文档、随机打乱顺序等多个消融上验证了趋势一致（Appendix A–C），主要结论的稳健性有旁证。

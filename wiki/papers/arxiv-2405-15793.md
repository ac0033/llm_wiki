# SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering

- 一手来源：https://arxiv.org/abs/2405.15793
- 作者：John Yang、Carlos E. Jimenez、Alexander Wettig、Kilian Lieret、Shunyu Yao、Karthik Narasimhan、Ofir Press（Princeton Language and Intelligence）
- 对应系统页：[[swe-agent]]

## 摘要

论文的出发点是：正如人类工程师受益于 IDE 这类专门软件，LM agent 是一类"新型终端用户"，也需要为它们专门设计的计算机接口。作者提出 ACI（Agent-Computer Interface，智能体-计算机接口）这一研究对象，主张在固定基座模型的前提下，接口设计（可用命令、环境反馈格式、历史管理）本身就是影响 agent 表现的独立变量。据此他们构建了 SWE-agent 系统，用定制的 ACI 让 LM 自主完成软件工程任务。在 SWE-bench 和 HumanEvalFix 上，SWE-agent 分别以 12.5% 和 87.7% 的 pass@1 取得当时的 SOTA，远超非交互式（RAG）基线。论文还通过消融实验给出了 ACI 设计如何影响 agent 行为与表现的实证分析。

## 要点

**问题设定与核心概念**

- 论文假设模型固定、只改接口：ACI 规定了 LM 可用的命令、环境状态如何回传给 LM，以及历史命令与观察如何被格式化组装成每一步的输入。
- 方法论借鉴 HCI：通过人工检查 agent 行为发现困难 + 在开发集上网格搜索来迭代接口设计。

**四条 ACI 设计原则**（论文第 2 节）

1. 动作要简单易懂：命令选项少、文档精简，减少对 demonstration 或微调的依赖。
2. 动作要紧凑高效：文件导航、编辑等关键操作应合并为尽可能少的动作，一步取得实质进展。
3. 环境反馈要有信息量但简洁：如编辑后自动展示更新内容，但不堆砌无关细节。
4. 防护栏（guardrails）缓解错误传播：如编辑命令内置代码 linter，引入语法错误的编辑被拒绝并要求重试。

**SWE-agent 的 ACI 组成**（论文第 3 节）

- 搜索导航：`find_file` / `search_file` / `search_dir`，结果做摘要式展示，单次查询最多返回 50 条，超出则不返回结果并提示 agent 写更精确的查询。
- 文件查看器：每次最多显示 100 行窗口，带行号、文件总行数、上下省略行数提示，支持 `scroll_down` / `scroll_up` / `goto`。
- 文件编辑器：`edit` 命令与查看器联动，按起止行号替换内容，编辑后自动回显更新结果；linter 检出错误的编辑被丢弃。
- 上下文管理：每步要求模型输出 thought + command（ReAct 式，[62]）；第 5 条之前的历史观察各自折叠为一行，保留计划与动作历史的同时压缩上下文。
- 系统构建在 Linux shell 之上，保留常用 bash 命令；推理与评测均在 Docker 沙箱容器中执行。

**实验设置与主要结果**（论文第 4、5 节）

- 数据：SWE-bench 全集 2,294 个任务实例（12 个 Python 仓库），消融在 300 实例的 SWE-bench Lite 上进行；另用 HumanEvalFix 测短代码调试能力。
- 模型：GPT-4 Turbo（gpt-4-1106-preview）与 Claude 3 Opus；作者试过 Llama 3、DeepSeek Coder 等但表现不佳（如 Llama 3 的 8k 上下文窗口太小）。
- 主结果：SWE-agent + GPT-4 Turbo 在 SWE-bench 全集解决 12.47%（286/2,294）、Lite 上 18.00%（54/300）；+ Claude 3 Opus 为 10.46% / 13.00%。对照 RAG 基线（GPT-4 Turbo 全集 1.31%、Lite 2.67%），Lite 上解决率提升约 6.7 倍（成本是 RAG 的 8–13 倍，平均每个成功实例约 $1.59–1.67）。
- ACI 价值的直接对照：同为 GPT-4 Turbo，Shell-only（沿用 InterCode 式裸 shell 交互）在 Lite 上为 11.00%，SWE-agent 的 18.00% 相对提升约 64%。
- HumanEvalFix：SWE-agent + GPT-4 Turbo 的 pass@1 为 Python 87.7%、JS 89.7%、Java 87.9%，摘要口径为 87.7%（正文表述为 88.3%，见"可质疑之处"）。
- 消融（SWE-bench Lite）：带 lint 守卫的 edit 18.0% vs 无守卫 15.0% vs 无编辑命令 10.3%；摘要式搜索 18.0% vs 逐条翻页式搜索 12.0%（比无搜索工具 15.7% 还差）vs 无搜索 15.7%；查看器窗口 100 行 18.0% vs 30 行 14.3% vs 全文 12.7%；只保留最近 5 条观察 18.0% vs 完整历史 15.0%。
- 其他：单个实例预算上限 $4，超支则自动提交已有修改；成功率与 issue 年龄不相关（用于排除测试集污染，附录 B.2）；2,294 个实例中 51.7%（1,185 个）的轨迹至少出现过一次失败编辑，说明编辑防护栏是高频用到的机制而非摆设。

## 与本库的关系

- 这篇论文是本库 [[agent-harness]] 概念页"Harness 是独立性能杠杆"论断的关键实证：固定基座模型、只重设计 ACI，就在 [[swe-bench]] 上把 Lite 解决率从 11.00%（Shell-only）提到 18.00%。
- 按六组件拆解，它的贡献集中在 [[action-interface]]（紧凑的 edit/search 命令）与 [[observation-interface]]（100 行窗口、摘要式搜索结果），辅以 [[context-manager]]（历史观察折叠）和 [[verification-governance]]（编辑 lint 守卫、Docker 沙箱）；控制循环保持最简的 [[react]] 式单循环，复杂度刻意压到接口层。
- 对应系统页 [[swe-agent]] 从工程实现角度描述了同一系统，两页互为补充。
- 论文第 2 节的四条设计原则与 [[harness-vs-model-evaluation]] 讨论的"harness 与模型共同演化"问题直接相关：SWE-agent 的 ACI 是围绕 SWE-bench 任务打磨的。
- 同出 Princeton 的 [[swe-bench]]（Jimenez et al.）是其评测基准与 RAG 基线来源。

## 可质疑之处

- **数字的时效性**：12.5% 是 2024 年上半年的 SOTA，此后 SWE-bench 榜单（尤其 Verified 子集）已被大幅刷新，引用时须注明这是论文发表时的结果，不能代表 SWE-agent 现行版本的水平。
- **过拟合 benchmark 的风险**：ACI 是作者在 SWE-bench 开发集上人工迭代 + 网格搜索打磨出来的，论文自己在 Limitations 中承认系统范围限于软件工程/代码任务，ACI 原则能否迁移到其他领域（web 购物、知识库导航等）待验证。
- **HumanEvalFix 口径不一致**：摘要写 87.7%，正文写 88.3%，表格分语言给出 Python 87.7 / JS 89.7 / Java 87.9。88.3% 的来源（可能是三语言平均）论文未明说，待验证。
- **归因颗粒度**：与 Shell-only 的对照固定了模型，但 SWE-agent 同时改了命令集、反馈格式、历史管理与 demonstration，无法从该对照中分离单个 ACI 因素的贡献；单因素消融只在 Lite 子集上进行，全集上的归因证据不足。
- **pass@k 与方差**：论文报告 6 次运行下平均方差较低，但单个实例的解决结果波动大（Figure 4），单次运行的 % Resolved 作为结论的稳健性有限。

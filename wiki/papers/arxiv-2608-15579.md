# Kozuchi Agent: A Language-Agnostic Open-Weight Agent for Software Repair

> ASE '26 经验报告（Fujitsu Research 团队，Bahrami 等）。raw 快照：`raw/papers/arxiv-2608.15579.pdf`。

## 摘要

这篇经验报告回答一个工业问题：把开放权重、本地托管的模型放进一个可审计的修复 harness 里，配合跨 agent 的测试时选择，能走多远？作者构建了 Kozuchi Agent——一个语言无关的 issue-to-patch agent，底座是 mini-swe-agent，外面包了显式阶段图、持久化共享状态、确定性工具沙箱和模型无关的动作接口，整套评测由 CI 流水线驱动。在 SWE-bench Verified 官方评测器上，本地托管的 Qwen3.5-27B（无微调、TTS@8）解决 374/500 实例（74.80%，Wilson 95% CI [70.82%, 78.41%]）；同一 harness 不加改动迁到 Multi-SWE-bench Java，解决 41/128（32.03%），在严格开放权重提交中排名第一。

## 要点

**针对的四个工程痛点（harness 视角而非模型视角）：**

1. 长程执行：一次真实修复要复现 bug、生成回归测试、定位根因、改多个文件、验证结果，自由规划的 agent 在长轨迹上会跳过复现、重复调研。
2. 工具语法漂移：不同模型家族的 tool-call 约定不同，小的语法不匹配会让合理动作作废——harness 必须吸收这种多样性。
3. 多集群异构：GPU 推理、VM 测试、Docker 评分各跑各的，需要一套运行时屏蔽差异。
4. 评测成本：端到端重跑 SWE-bench Verified 太贵，CI 复用模式每次迭代短路 9 个阶段中的 6 个。

**关键机制（对应 harness 六组件）：**

- **阶段驱动的 [[control-loop]]**：把修复分解为 8 个语义阶段（issue 复现、FAIL-to-PASS 测试合成、代码定位、PASS-to-PASS 测试定位、修复、补丁验证、收尾、报告）、15 条正常/回退边的有向图；每个阶段退出时写 handover memo，记录携带的证据和未决风险。
- **模型无关的 [[action-interface]]**：每回合必须恰好产生一个可解析动作；4 种表面格式 × 17 个模型配置共用同一逻辑契约。Orchestra runtime 用「planner 起草意图 + formatter 只改写可执行命令」的双角色分工，作为微调的 harness 级替代。
- **确定性工具沙箱**：只有 line_trace（动态行追踪）、caller_trace（调用者发现）、line_edit（带预期目标行的守卫式编辑）三个工具；14 个按阶段和工具门控注入的 skill（纯 prompt 指导块，非学习能力）。
- **文件系统作为持久记忆（[[state-artifact-store]] / [[context-manager]]）**：阶段切换或阶段过长时写压缩 memo 进共享工件存储，「文件系统而不是原始对话」是持久记忆，防止上下文压缩丢掉证据。
- **跨 agent 测试时选择（[[verification-governance]]）**：K=8 次独立运行各自产出补丁和自己生成的 bug 揭示测试与回归测试；选择器把 run j 的归档测试交叉应用到 run i 的补丁上，构成 K×K 矩阵，score(i) = 0.3·B + 0.7·R（回归权重更高，因为合并后回归代价更大），不使用隐藏基准测试、不用学习型验证器。平票（10⁻³ 以内，304/495 实例）按更短补丁打破。

**结果与失败模式：**

- 选择器比按顺序取首个候选的基线多解决 +14 个实例（376 vs 362，内部 Docker 复评）；oracle 上限（8 次运行至少一次解决）是 408，选择器达到其约 92%。
- 495 条轨迹全部可对照配置的阶段图审计；494/495 补丁干净应用。
- 剩余 126 个未解决实例中 91.3% 是「补丁能应用但没过隐藏测试」的语义正确性问题，0% 是 diff 格式错误——残余差距在语义和选择，不在编辑格式。
- 跨语言迁移：Java 上每阶段 assistant 消息占比与 Python 相差 ±5 个百分点以内，同一 27B backbone 比最强同类开放权重 Java 对手（Qwen2.5-72B）多解决 38 个实例。
- 运营上，每个评测周期的人工触点从 5 个降到 1 个（一次 CI push），支撑「CI 即评测基座」的主张。

## 与本库的关系

- 这是 [[agent-harness]]「harness 是独立性能杠杆」主张的工业级实证：固定 27B 开放权重模型、不做微调，成绩全部来自阶段分解、动作契约、持久状态、确定性工具和测试时选择这些 harness 工程。
- 跨 agent 选择器是 [[verification-governance]] 的一个具体实现：在没有隐藏测试可用的选择时刻，把各候选运行自生成的测试交叉应用为选择证据，约束与生产环境「合并前无真实反馈」一致。
- 与 [[swe-agent]]：底座 mini-swe-agent 来自 SWE-agent 作者团队；Kozuchi 在其最小循环上加阶段契约和工具沙箱。与 [[openhands]]、AGENTLESS 是互补的开放软件 agent 平台。
- 对 [[swe-bench]] 页：提供了 2026 年开放权重系统在 Verified 上的参照点（374/500，官方评测器），以及 Multi-SWE-bench Java 跨语言迁移的证据。
- 对 [[agent-evaluation]]：报告了 Wilson CI、按仓库聚类的 bootstrap、配对 McNemar 检验加 Benjamini–Hochberg FDR 校正，是 benchmark 结果统计报告规范的示范。

## 可质疑之处

- **机制级消融缺失（作者自己声明的证据边界）**：阶段图、handover 状态、formatter、工具沙箱、CI 复用都只有运行特征（operational signatures）和工件审计支撑，未做组件移除实验；受控消融的只有候选数 K=8 和选择器。因此「每个机制各自贡献多少」待验证。
- **选择器效率**：线性插值显示跨 agent 选择器约相当于 oracle k≈2.2 的水平——8 份算力中大部分候选生成开销未被选择器兑现，selector regret 34/500（6.8pp）。
- **工业影响是估计值**：Table 2 的工程师分钟节省是数量级估计，非受控开发者实验；生产部署、终端用户 KPI 明确不在范围内。
- **单 backbone**：headline 结果只用 Qwen3.5-27B；harness 对其他模型家族的泛化虽有 17 配置的格式清单支撑，但分数层面的跨模型对照待验证。
- 工业影响的证据边界（Table 1）和工件发布范围（内部集群配置、pipeline 源码不在发布边界内）意味着外部团队无法完整复现 CI 侧，只能复现 agent 与选择器侧。
